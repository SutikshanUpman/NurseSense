# NurseSense (formerly MediGuard-AI): Alarm Budget

**Does limited-alert ICU monitoring actually need reinforcement learning, or is a well-tuned rule enough?**

This project tests that question in a small, reproducible simulator. It does not claim RL wins. It measures when it does and when it does not.

> **Phase 1** was a team project for the Meta PyTorch x Scaler OpenEnv Hackathon 2026 (Sutikshan Upman, Rajveer Gupta, Abdul Malik). Its full history is preserved in this repo under the tag `phase1-hackathon`.
> **Phase 2 onward** is a simplified rebuild focused on one research question.

---

## 1. The problem

ICU monitors raise far more alarms than needed. Staff learn to ignore them (**alarm fatigue**), and a real emergency can get lost in the noise.

Two things make this hard:

- **Every patient has a different normal.** A chronically hypertensive patient's BP is always high. A fixed threshold alarms on them all day.
- **Real deterioration is usually slow.** A gradual fever or falling SpO2 drifts the patient's own baseline with it, so "deviation from baseline" alone can look small.

*In plain words: a smoke alarm that rings every time you cook gets ignored, including on the day there is a real fire.*

## 2. The question

A nurse can only act on a limited number of alerts per shift. Every alert spent on a false alarm is one fewer for a real emergency. This makes the decision **sequential**: *today's alert changes what I can do later.*

**Hypothesis:** when alerts are limited, a learned policy (RL) can time alerts better than a tuned rule.

**Honest caveat:** a smart rule can also become budget-aware (for example, raise the threshold when few alerts remain). So the rule is tuned properly and RL has to beat that, not a weak baseline.

## 3. Why RL (and where it is not needed)

| Need | Does it require RL? |
|---|---|
| Compare a reading to this patient's own normal | **No.** A rolling average does this. |
| Decide *when* to spend a limited alert budget | **Possibly.** This is the part RL is tested on. |
| Weigh "alert now" against "wait for more evidence" on a slow trend | **Possibly.** Timing trade-off. |

RL is not used here because it is fashionable. It is used because the budget makes the problem sequential, and the project checks whether that actually matters. If the tuned rule matches RL, the finding is "the rule is enough, and it is cheaper and easier to trust."

*In plain words: RL is a trial-and-error learner. It plays thousands of simulated nights, gets a score at the end of each decision, and adjusts. No one tells it the right answer.*

## 4. Setup

- **One patient**, 60 steps per episode (1 step = 1 minute), generated by a seeded simulator.
- **Emergencies:** sudden spike and slow deterioration. Slow deterioration is more common, so it appears more often.
- **Actions:** `Ignore` or `Alert`.
- **Alert budget:** a parameter (swept from 1 to 10). It is a *soft* limit: extra alerts cost more but are not forbidden, and an extreme reading triggers a safety override.

**What the agent sees (about 5 numbers):**

1. Deviation from the patient's rolling 3-hour baseline
2. Trend (slope), so slow drifts are not hidden by the baseline
3. Alerts remaining
4. Time since the last alert

**Personalization** comes from the baseline calculation, not from a separate model per patient. One shared policy works on any new patient immediately.

**Reward:**

- Correct alert: positive
- False alert: small penalty, growing with fatigue
- Missed emergency: large penalty (otherwise the agent learns to ignore everything)

## 5. Approaches compared

1. **Fixed threshold:** population-style cutoff.
2. **Tuned budget-aware rule:** threshold chosen by grid search, adjusted by alerts remaining.
3. **DQN:** small neural network (about 2 layers x 64 units), trained from scratch on CPU. Weights are frozen after training.

*Planned later (Phase 4):* an oracle that sees the future, used as an upper bound.

## 6. How success is measured

- **Gate:** missed emergencies must be 5% or lower. Agents that miss more are not ranked.
- **Win condition:** fewer false alerts per night at that same miss rate.
- **Also reported:** detection delay (time from onset to alert).
- **Evaluation:** 3-5 random seeds, with the budget swept from 1 to 10.

*In plain words: same safety, less noise.*

## 8. Limitations

- **Simulation only.** No real patient data.
- **Reward comes from simulator labels.** A real deployment would need clinician-confirmed events.
- **The fatigue model is an assumption.** It will be checked with a sensitivity analysis rather than treated as fact.
- **Not a clinical tool.**
